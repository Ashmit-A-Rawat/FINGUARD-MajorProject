# KYC entity resolution (`kyc/`)

**Task.** Given a KYC document (name, DOB, address), find the customer-master records of the *same
entity*. The output is never just "match = true": every candidate carries all intermediate evidence.

```
KYC document -> canonical identity (Phase 3 normalisation)
  -> first-stage signals per customer (best over primary + alternate names)
       exact | fuzzy | BM25 (word) | BM25 (char trigram) | dense embedding
  -> hybrid = alpha*BM25 + (1-alpha)*dense          -> top-K candidates (K=20)
  -> learned reranker (name-only features)          -> P(same entity | name)
  -> structured verification (DOB, address)         -> agreement score + contradictions
  -> final_score = (w_name*name_score + w_struct*structured) / (w_name+w_struct)
  -> KYCMatchResult (scores, is_match, confidence, match_reasons, contradictory_evidence)
```

## Stages

| Stage | Code | Notes |
|---|---|---|
| A exact | `kyc/lexical/exact.py` | identical canonical name AND identical DOB |
| B fuzzy | `kyc/lexical/fuzzy.py` | rapidfuzz token-sort ratio |
| C BM25 | `kyc/lexical/bm25.py` | own implementation (about 50 lines). Score divided by the query's *self-score* (ceiling), so it is in [0,1] and thresholds are comparable across queries. Unseen tokens still raise the ceiling. A char-trigram variant is included as an extra baseline. |
| D dense | `kyc/semantic/` | `sentence-transformers/all-MiniLM-L6-v2` (384-d, about 90 MB, runs on CPU). Embedder is an interface (`Embedder`); tests use a fake. |
| E hybrid | `kyc/systems.py` | weighted sum of normalised BM25 and cosine; alpha=0.5 fixed a priori (not tuned) |
| F rerank | `kyc/reranking/` | `HistGradientBoostingClassifier` on pairwise name features (Jaro-Winkler on full/first/last, token-set ratio, initial compatibility, middle-name compatibility, reordered/initials flags, plus the first-stage signals). **Name-only**: it never sees DOB or address. |
| G structured | `kyc/scoring/structured.py` | DOB exact=1, day/month transposition=0.5 (flagged), else 0; address scored per component (number .25, street .25, city .30, country .20). Missing query fields are neutral (weights renormalised). Every disagreement becomes a `contradictory_evidence` string. |

## Design decisions

- **Why the reranker is a small learned model rather than an off-the-shelf cross-encoder.**
  Public cross-encoders (e.g. MS MARCO) are trained for passage relevance, not for judging whether
  two person names refer to the same identity. We train on our own benchmark instead.
  This is a trade-off: it is only as good as the synthetic training distribution.
- **Why name and structured evidence are separate.** Namesakes have identical names by
  construction, so a name-only model cannot separate them; DOB/address must. Keeping the stages separate
  lets the ablation show what each contributes.
- **Reranker never sees the test split**, and thresholds are chosen on dev only (see evaluation plan).
- **Alternate names** are indexed as extra entries; a customer's score is the max over its entries.

## Known limitations

- Benchmark queries are KYC documents of the *same synthetic population* the master was built from.
  DOB is uniformly random and addresses come from small pools, so structured verification is far more
  discriminative here than it would be on real data. Treat absolute numbers with caution.
- Name variations are generated by a fixed set of rules (typo, initials, listed transliterations,
  middle-name change, reordering), so real-world variation is broader.
- The default `match_threshold` (0.65) is a priori; the benchmark reports per-system thresholds
  learned on dev, and a deployment must re-calibrate on its own data.
- The reranker model is not yet persisted to disk (refit each benchmark run).
